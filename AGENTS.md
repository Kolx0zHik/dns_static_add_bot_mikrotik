# AGENTS.md

# Общие сведения

Данный проект представляет собой Telegram-бота для безопасственного управления маршрутизаторами MikroTik по SSH.

Основная цель проекта — создать легко расширяемую систему автоматизации, пригодную для дальнейшего развития.

Перед внесением изменений необходимо ознакомиться с файлом `requirements.md`.

---

# Основные принципы разработки

## Архитектура

Строго соблюдать модульную архитектуру.

Не допускать смешивания:

- Telegram API;
- бизнес-логики;
- SSH-взаимодействия;
- конфигурации;
- утилитарных функций.

Каждый слой должен отвечать только за свою область ответственности.

---

## Работа с MikroTik

Любое взаимодействие с MikroTik должно происходить исключительно через сервисный слой.

Запрещается:

- выполнять SSH-команды непосредственно из Handler;
- дублировать код подключения;
- хранить RouterOS-команды в нескольких местах.

Все RouterOS-команды должны быть централизованы.

Проект поддерживает несколько MikroTik. Конфигурация роутеров хранится в `.env`
через `MIKROTIK_ROUTERS` и переменные `MIKROTIK_<ID>_*`.
Разграничение доступа выполняется по `MIKROTIK_<ID>_ALLOWED_USERS`.
При добавлении новых операций нельзя обходить каталог роутеров и проверку доступа.

---

## Работа с Telegram

Handler должен:

- принимать сообщение;
- валидировать входные данные;
- вызывать соответствующий сервис;
- формировать ответ пользователю.

Любая бизнес-логика внутри Handler считается ошибкой архитектуры.

---

## Код

Использовать:

- Python 3.13+
- aiogram 3.x
- строгую типизацию;
- современные возможности Python;
- dataclass там, где это уместно.

Следовать принципам:

- SOLID;
- DRY;
- KISS;
- YAGNI.

---

## Конфигурация

Любые параметры должны храниться только в `.env`.

Запрещается:

- хранить пароли;
- хранить токены;
- хранить IP-адреса;
- хранить Telegram ID;
- хранить SSH-учётные данные в коде.

---

## Логирование

Все ошибки должны логироваться.

Все действия пользователей должны логироваться.

Логи должны помогать диагностировать проблему без необходимости воспроизводить её вручную.

---

## Обработка ошибок

Любая потенциальная ошибка должна быть обработана.

Пользователь никогда не должен видеть:

- traceback;
- внутренние исключения;
- технические сообщения Python.

Все ошибки должны быть преобразованы в понятные сообщения.

---

## Интерфейс

Использовать только Inline Keyboard.

Интерфейс должен быть минималистичным.

Все операции должны сопровождаться понятными сообщениями.

Для потенциально опасных действий всегда использовать подтверждение.

---

## Расширяемость

При написании нового кода необходимо предполагать дальнейшее развитие проекта.

Добавление нового функционала не должно требовать изменения существующих модулей.

Предпочитать композицию наследованию.

Новые команды должны оформляться в виде отдельных сервисов или модулей.

---

## Качество кода

Перед завершением любой задачи необходимо убедиться, что:

- отсутствует дублирование кода;
- соблюдены принципы архитектуры;
- все функции имеют понятные названия;
- нет "магических" значений;
- код проходит Ruff и Black;
- при необходимости добавлены тесты.

---

## Документирование

При добавлении нового функционала необходимо:

- обновить документацию;
- при необходимости обновить README;
- поддерживать актуальность `requirements.md`.

---

## Что запрещено

Не допускается:

- писать бизнес-логику в Handler;
- использовать глобальные переменные;
- дублировать SSH-код;
- хранить секреты в репозитории;
- выполнять небезопасные RouterOS-команды без подтверждения пользователя;
- ухудшать читаемость существующего кода.

2. Надёжность.
