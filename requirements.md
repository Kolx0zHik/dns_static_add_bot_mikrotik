# Telegram-бот для управления MikroTik

## 1. Общая информация

### Цель проекта

Разработать Telegram-бота для безопасного управления маршрутизаторами MikroTik по SSH.

На первом этапе бот предназначен для автоматического добавления DNS Static записей типа **FWD**, а архитектура проекта должна позволять без существенной переработки добавлять новые функции управления MikroTik.

Проект должен быть полностью контейнеризирован, поддерживать автоматическую сборку Docker-образов и соответствовать современным практикам разработки.

Проект должен иметь модульную архитектуру.

Пример структуры:

```
app/
│
├── bot.py
├── config.py
├── handlers/
├── keyboards/
├── middlewares/
├── filters/
├── states/
├── validators/
├── services/
│   ├── mikrotik.py

- SSH-код должен быть централизован.
- Новые функции должны добавляться независимо от существующих модулей.

Пример:

```

MIKROTIK_HOST=
MIKROTIK_PORT=22

Запрещается хранить секреты в исходном коде.

---

# 5. Авторизация пользователей

Бот должен принимать команды только от пользователей, перечисленных в списке разрешённых Telegram ID.

Для остальных пользователей:

- никаких действий не выполнять;
- выводить сообщение:

> Доступ запрещён.

---

# 6. Первый реализуемый сценарий

Пользователь отправляет команду:

```
/add
```

После этого бот предлагает ввести доменное имя.

Например:

```
example.com
```

---

# 7. Проверка введённого домена

Перед выполнением команды необходимо выполнить полную проверку.

## Необходимо

- удалить пробелы по краям;
- привести домен к нижнему регистру;
- проверить корректность DNS-имени согласно RFC;
- разрешить только латинские буквы, цифры, дефис и точки;
- проверить максимальную длину домена;
- проверить длину каждой метки;
- запретить двойные точки;
- запретить точку в начале;
- запретить точку в конце.

## Необходимо запретить

```
http://
https://
ftp://
```

Также необходимо запретить:

```
/
\
?
#
&
:
%
@
```

Недопустимые примеры:

```
https://example.com
http://example.com
example.com/
example.com/test
192.168.1.1
example..com
.example.com
example.com.
```

После обнаружения ошибки бот должен вывести понятное описание проблемы.

---

# 8. Проверка существующей записи

Перед добавлением необходимо проверить наличие записи на MikroTik.

Если запись уже существует, необходимо вывести сообщение:

> Запись уже существует.

Изменения в конфигурацию не вносить.

---

# 9. Добавление записи

После успешной проверки бот показывает подтверждение.

Пример:

```
Добавить запись?

example.com
```

Кнопки:

- ✅ Добавить
- ❌ Отмена

После подтверждения бот выполняет команду:

```
/ip dns static add \
name="example.com" \
type=FWD \
forward-to=CloudFlare \
ttl=1d \
match-subdomain=yes \
address-list="to-VPN"
```

После успешного выполнения вывести сообщение:

> Запись успешно добавлена.

---

# 10. Интерфейс

Использовать исключительно Inline Keyboard.

Не использовать Reply Keyboard.

Каждое действие пользователя должно сопровождаться понятными сообщениями.

После выполнения операций клавиатуры должны обновляться.

---

# 11. Обработка ошибок

Необходимо предусмотреть обработку всех типовых ошибок.

Например:

- SSH недоступен;
- неверный пароль;
- неверный пользователь;
- потеря соединения;
- таймаут;
- ошибка выполнения команды;
- ошибка валидации;
- запись уже существует;
- пользователь нажал кнопку повторно;
- пользователь отменил операцию;
- пользователь прислал фото;
- пользователь прислал документ;
- пользователь прислал видео;
- пользователь прислал стикер;
- пустое сообщение;
- слишком длинное сообщение;
- сообщение не является текстом.

Пользователь никогда не должен видеть traceback или внутренние ошибки приложения.

- успешные команды;
- ошибки;
- Telegram ID пользователя;
- выполняемые действия;
- время выполнения операций.

# 13. Docker

Проект должен запускаться одной командой:

```
docker compose up -d
```

Все необходимые сервисы должны запускаться автоматически.

---

# 14. CI/CD

При каждом Push в ветку main GitHub Actions должны автоматически:

1. Проверить форматирование (Black).
2. Проверить стиль кода (Ruff).
3. Запустить тесты.
4. Собрать Docker Image.
5. Опубликовать образ в GitHub Container Registry (GHCR).

Сборка должна останавливаться при любой ошибке.

---

# 15. Требования к коду

Использовать:

- type hints;
- dataclass при необходимости;
- SOLID;
- DRY;
- KISS;
- понятные имена функций;
- документирование публичных методов.

Код должен быть читаемым и легко расширяемым.
