# Telegram-бот для управления MikroTik

## 1. Общая информация

### Цель проекта

Разработать Telegram-бота для безопасного управления маршрутизаторами MikroTik по SSH.

На первом этапе бот предназначен для автоматического добавления DNS Static записей типа **FWD**, а архитектура проекта должна позволять без существенной переработки добавлять новые функции управления MikroTik.

Проект должен быть полностью контейнеризирован, поддерживать автоматическую сборку Docker-образов и соответствовать современным практикам разработки.

## Требования

- Telegram Handler не должен содержать бизнес-логику.
- Работа с MikroTik должна выполняться только через сервисный слой.
- SSH-код должен быть централизован.
- Новые функции должны добавляться независимо от существующих модулей.
- Выбор MikroTik и проверка доступа должны быть отделены от SSH-взаимодействия.
- RouterOS-команды не должны зависеть от Telegram-слоя.

# 4. Конфигурация

Все параметры должны храниться в `.env`.

Пример:

```
BOT_TOKEN=
ALLOWED_USERS=11111111,22222222

MIKROTIK_HOST=
MIKROTIK_PORT=22
MIKROTIK_USER=
MIKROTIK_PASSWORD=
```

Для нескольких MikroTik используется расширенный формат:

```
BOT_TOKEN=
SSH_TIMEOUT=10

MIKROTIK_ROUTERS=office,home

MIKROTIK_OFFICE_NAME=Office MikroTik
MIKROTIK_OFFICE_HOST=
MIKROTIK_OFFICE_PORT=22
MIKROTIK_OFFICE_USER=
MIKROTIK_OFFICE_PASSWORD=
MIKROTIK_OFFICE_ALLOWED_USERS=11111111,22222222

MIKROTIK_HOME_NAME=Home MikroTik
MIKROTIK_HOME_HOST=
MIKROTIK_HOME_PORT=22
MIKROTIK_HOME_USER=
MIKROTIK_HOME_PASSWORD=
MIKROTIK_HOME_ALLOWED_USERS=22222222
```

`ALLOWED_USERS` может использоваться как общий список доступа для всех роутеров,
но для разграничения прав необходимо задавать `MIKROTIK_<ID>_ALLOWED_USERS`.
ID роутера должен состоять из латинских букв, цифр и подчёркивания.

Запрещается хранить секреты в исходном коде.

# 5. Авторизация пользователей

Бот должен принимать команды только от пользователей, которым разрешён доступ хотя бы к одному MikroTik.
Доступ к конкретным MikroTik должен разграничиваться по Telegram ID.

Для остальных пользователей:

- никаких действий не выполнять;
- выводить сообщение:

> Доступ запрещён.

После авторизации пользователь должен видеть только доступные ему MikroTik.
Если доступен один MikroTik, бот может сразу открывать меню действий.
Если доступно несколько MikroTik, бот должен сначала предложить выбор роутера.

---

# 6. Первый реализуемый сценарий

Пользователь отправляет команду:

```
/add
```

Если пользователю доступен один MikroTik, бот сразу предлагает ввести одно или несколько доменных имён.
Если доступно несколько MikroTik, бот сначала предлагает выбрать роутер.

Доменные имена передаются одним текстовым сообщением, каждый домен с новой строки.
Суммарная длина списка ограничивается так, чтобы подтверждение и итог операции
помещались в одно сообщение Telegram.

Например:

```
example.com
sub.example.com
```

---

# 7. Проверка введённого домена

Перед выполнением команды необходимо проверить каждую непустую строку списка. При
ошибке бот должен указать номер строки и не выполнять добавление ни одного домена.
Повторяющиеся домены в одном списке необходимо отклонять.

## Необходимо

- удалить пробелы по краям;
- привести домен к нижнему регистру;
- проверить корректность DNS-имени согласно RFC;
- разрешить только латинские буквы, цифры, дефис и точки;
- проверить максимальную длину домена;
- проверить длину каждой метки;
- запретить двойные точки;
- запретить точку в начале;
- запретить точку в конце.

## Необходимо запретить

```
http://
https://
ftp://
```

Также необходимо запретить:

```
/
\
?
#
&
:
%
@
```

Недопустимые примеры:

```
https://example.com
http://example.com
example.com/
example.com/test
192.168.1.1
example..com
.example.com
example.com.
```

После обнаружения ошибки бот должен вывести понятное описание проблемы.

---

# 8. Проверка существующей записи

Перед добавлением необходимо проверить наличие записи на MikroTik.

Если запись уже существует, её необходимо пропустить и указать в итоговом сообщении:

> Запись уже существует.

Повторную запись в конфигурацию не вносить. Остальные домены списка необходимо
обработать.

---

# 9. Добавление записи

После успешной проверки бот показывает весь список и одно общее подтверждение.

Пример:

```
Добавить записи?

example.com
sub.example.com
```

Кнопки:

- ✅ Добавить
- ❌ Отмена

После подтверждения бот выполняет команду:

```
/ip dns static add \
name="example.com" \
type=FWD \
forward-to=CloudFlare \
ttl=1d \
match-subdomain=yes \
address-list="to-VPN"
```

После выполнения вывести количество добавленных и уже существовавших записей, а
также соответствующие списки доменов.

> Запись успешно добавлена.

# 10. Интерфейс

Использовать исключительно Inline Keyboard.

Не использовать Reply Keyboard.

Каждое действие пользователя должно сопровождаться понятными сообщениями.

После выполнения операций клавиатуры должны обновляться.

---

# 11. Обработка ошибок

Необходимо предусмотреть обработку всех типовых ошибок.

Например:

- SSH недоступен;
- неверный пароль;
- неверный пользователь;
- потеря соединения;
- таймаут;
- ошибка выполнения команды;
- ошибка валидации;
- запись уже существует;
- пользователь нажал кнопку повторно;
- пользователь отменил операцию;
- пользователь прислал фото;
- пользователь прислал документ;
- пользователь прислал видео;
- пользователь прислал стикер;
- пустое сообщение;
- слишком длинное сообщение;
- сообщение не является текстом.

Пользователь никогда не должен видеть traceback или внутренние ошибки приложения.

# 13. Docker

Проект должен запускаться одной командой:

```
docker compose up -d
```

Все необходимые сервисы должны запускаться автоматически.

---

# 14. CI/CD

При каждом Push в ветку main GitHub Actions должны автоматически:

1. Проверить форматирование (Black).
2. Проверить стиль кода (Ruff).
3. Запустить тесты.
4. Собрать Docker Image.
5. Опубликовать образ в GitHub Container Registry (GHCR).

Сборка должна останавливаться при любой ошибке.
